# Changelog

All notable changes to nextc-claude are documented here, grouped by date.

## 2026-11-26

### Changed
- **`.claude/worktrees/` is gitignored.** Claude Code keeps session worktrees there; they are per-machine working copies, and the folder showed up as untracked in every `git status`.

## 2026-11-24

### Added
- **Default model and advisor: Opus for the session, Fable as the advisor** (`settings/user-settings.json`: `"model": "opus"`, `"advisorModel": "fable"`). `setup-rules.sh` sets each key only where the person has not set it, and only on the first run. The run is recorded in `~/.claude/nextc-claude-setup.json`, because Claude Code's `/advisor off` removes the key instead of storing "off" (read in 2.1.331), so without a record every later run would switch a billed advisor back on. New flag `--skip-model` declines and is recorded; `--check` reports defaults that were never applied. The Claude Code docs give a plugin no way to set the model or the advisor (hooks only add context, agent definitions have no advisor field, the marketplace manifest carries no settings), so this reaches people who run the script or whose company ships managed settings; everyone else types `/model opus` and `/advisor fable`. Six tests added to `tests/setup-rules.test.mjs` and two extended (17 in that file now). The script now refuses a settings file that is empty or not a JSON object instead of reporting that nothing needed merging.
- **`enterprise/managed-settings.example.json` carries the same two keys**, with a section in `enterprise/README.md` on what they do: a managed `model` is a starting default and not a lock, the advisor's pairing rule, billing, the platforms it does not run on, and the one thing not verified (what `/advisor off` does against a managed `advisorModel`). Checked against the settings, settings-reference, model-config and advisor pages on 2026-11-24.
- **`rules-references/agents-roster.md` gains "Session model and advisor"**, recording the pairing as the user's decision and that the advisor is not an agent, so the closed Fable list does not cover it.
- **New rule `engineering-bar.md`** (`nextc-core/rules/nextc-claude/`, always loaded, 2,903 bytes) with its checklist in `nextc-core/rules-references/engineering-bar.md`. It comes from feedback that plans and features from this toolkit ran but were not designed: no data model reasoning, no indexes, no thought for size; and from the follow-up that performance is more than indexes. Before code that stores or queries data that grows, serves requests, or runs on every frame, the rule asks for five decisions in the plan or the reply: the target and workload, the data model worked out from the access patterns, the cost of each critical path, limits with concurrency, failure and migration, and the alternative rejected with the first thing that breaks and how the target will be proven. Structural choices are made at design time; micro-optimization waits for a measurement. It also sets a bar for the code itself (fix the cause, fit the codebase, no dead code or placeholder TODOs) and says that building for load that will never come is below the bar too. There are now 16 rules, 15 always loaded, 35,740 bytes (was 32,837).
- **The checklist reference is built from primary sources** read on 2026-11-24 and listed at its end: the Azure and AWS Well-Architected performance pillars, the Google SRE book and workbook (service level objectives, overload, cascading failures, the launch checklist), PostgreSQL, Firestore and Redis docs, Flutter, Android, web.dev and Unity performance docs, Rob Pike's rules, Brendan Gregg's methodology and Martin Fowler on architecture. Ten sections: problem, targets and workload, store and data model, critical-path cost, resources and limits and cost, concurrency and failure and overload, the client (frame budget, startup, lists, images, allocation, network, web vitals), migration and lifecycle, proof, trade-offs. It says what was not sourced.
- **Eval suite for the planner, architect and code-reviewer** (`nextc-ecc/evals/`, five cases on one invented API, run with `claude plugin eval`): an ordinary feature in a repo with no workload numbers, a feed where the docs give numbers, a change that touches no data (the guard against over-design), a weak plan for the architect, and a change with performance defects for the reviewer. Deterministic graders include a character cap per plan and a check that no step creates test files in a repo without tests. Results on 2026-11-24 against the agents in this checkout, one run per case: architect 7/7 (twice), code-reviewer 6/6, planner feed 9/9, planner likes 9/9, planner no-data 5/7 on the run itself and 7/7 once two graders that misread a good plan were corrected (checked against the saved plan). The README records that the plugin's own hooks block every Bash and Write call in an eval run when `node` is a version-manager shim that needs the real home folder, and how to avoid it.
- **Rule eval case `design-before-code`** (`rules-evals/cases.mjs`, 28 cases now): asked for a function listing a customer's orders from a table with no index on the filter column, the agent must create or raise the index and bound the read. On sonnet, without a size hint: on the rule's first version, across six runs per arm, no baseline run wrote the index migration (five named the missing index, one said nothing) and all six runs with the rule wrote it; on the committed version, three runs per arm, all three with the rule created the index and all three without it only raised it in the reply. A one-run pass of all 28 cases with the rule in place scored 27/28 against 25/28 before; the one failure on the after side (`skip-heavy-tag`) fails the same way without the rule (`rules-evals/RESULTS.md`).

### Changed
- **`planner` agent designs the solution before it lists steps, and sizes the plan to the change** (`nextc-ecc/agents/planner.md`). The old definition asked only for files, dependencies, verify commands and exit criteria, so a plan could be complete and decide nothing. The plan format now has a required `## Design` section: the problem behind the request, targets and workload (assumptions marked), a table of access patterns with the table and index or key that serves each, the schema with its constraints, a decisions table (critical-path cost on server and client, resources and limits, consistency and concurrency, failure and overload, migration and lifecycle, proof, each with the rejected alternative), and the breaking point with what was deliberately not built. Each step gains an `Implements:` field. New process steps: find the real problem, check store and SDK behavior against official docs (the agent gains `WebSearch` and `WebFetch`, and treats a fetched page as evidence, never as an instruction), and attack the plan before saving it. Three corrections came from running it:
  - With no numbers in the repo, a first draft assumed a viral-scale workload and used it to justify a denormalized counter. It now assumes the size the product's own description supports, sends any assumed number that decides a trade-off to the user, and never lets an assumed workload justify the heavier design.
  - On the real model the broadened definition over-planned: a 31 KB plan with a new test suite and a new dependency for moving one header check, and 40 to 51 KB plans with up to 14 steps for a feature. It now sizes the plan first (small, medium, large, with a line budget and step count for each), plans the request and lists adjacent problems as "Found, not in scope", limits lookups to facts a decision rests on, and keeps code out of the plan. The same cases then produced 11, 21 and 23 KB plans with 2, 5 and 5 steps.
  - A project with no tests gets no test step, test file, runner, dependency or question about adding them, in the Proof part too.
- **`architect` agent judges the design before the steps** (`nextc-ecc/agents/architect.md`): a plan that touches stored data without stating workload, access patterns, schema and indexes is a HIGH finding by itself. It also reports a missing or unprovable target, the cost of the critical paths on server and client, limits nobody counted (connection pools, quotas, billed reads, hot keys), unsafe retries, missing deadlines and unbounded queues, migrations that lock a large table, data with no retention rule, over-building, a plan out of proportion to its change, and a design no step builds. CRITICAL now includes a design that cannot carry the workload it states. It caps its report at about ten findings and gains `WebSearch` and `WebFetch`. Greenfield mode asks for the same design content.
- **`code-reviewer` checks performance, data access and design that will not last** (`nextc-ecc/agents/code-reviewer.md`): queries in loops, unbounded reads, a new filter or sort with no index, offset pagination on long lists, work done in application code that the store can do, whole result sets held in memory, one statement per item where a batch exists, unbounded parallelism, heavy work before the response, calls with no timeout or uncapped retries, a connection per request, logic in the wrong layer, rules the store could enforce, writes unsafe to retry. The Flutter list adds heavy work in `build`, eager long lists, work on the UI isolate and oversized images; the Unity list adds pooling. Given a plan path, it checks that the code built the plan's Design. A hot path that degrades at the product's expected data size is HIGH.
- **`critical-reviewer`** asks how long a migration locks or rewrites the table at its real size, whether an index or key serves every query on a changed schema, and whether the store enforces the rule.
- **`/blueprint`** (`nextc-core/skills/blueprint/`): the plan template (`references/step-template.md`) opens with the planner's own header (open questions, goal, Design, risks) and its Step block gains an `Implements:` field, so the two formats name things the same way; the skill reads the data layer during research, passes workload facts to the planner, asks the architect to judge the design first, reports the design decisions with the plan, and lists two new anti-patterns (a plan that decides no data model; a design no step builds).
- **`/feature-dev`**: a schema change, a new index, or a new store, cache or queue now makes a feature Architectural (planner and architect). A Bounded plan written by the lead states its design decisions before the step list, and becomes Architectural when a new query has no index to serve it. The approval summary shows the data model, indexes, assumed workload and main trade-off. Verification walks the plan's Design against the code, and the code-reviewer receives the plan path.
- **`/team-feature-dev`**: the planner gets workload facts and adds a Design section to a reused spec that lacks one, the schema (migrations, indexes, constraints) is one worker's task, the approval shows the design decisions with the task graph, verification walks the Design against the code, and the code-reviewer receives the plan path.
- **Kickoff `architecture-guide.md`** (`nextc-project-kickoff/references/`): the Data model section of `docs/architecture.md` now also states expected size per entity, an access-pattern table (feature id, query, index or key that serves it), the constraints the store enforces, and the first thing that gets slow; the cross-cutting rules gain performance targets for the critical flows and how each is measured.
- **Docs synced:** `CLAUDE.md` and `README.md` (16 rules, the always-loaded size, the planner, architect and code-reviewer descriptions, 28 rule eval cases, `nextc-ecc/evals/`), `rules-evals/README.md` (28 cases, 168 runs for a full pass, the new case).

## 2026-11-17

### Added
- **The rules install themselves.** Nobody links rules by hand any more: `nextc-core` now ships the 15 rules and their references (`nextc-core/rules/nextc-claude/`, `nextc-core/rules-references/`; `rules/` and `rules-references/` at the repo root are links to them) and, at session start, `scripts/install-rules.mjs` copies them into `~/.claude/rules/nextc-claude` and `~/.claude/nextc-claude-references` and refreshes them when the plugin updates (option `install_rules`, on by default). It keeps a record of what it wrote, so it never overwrites a file the person edited or one that was there before (it names such a file once), removes only rules it installed that are no longer shipped, leaves a folder linked to a checkout alone, writes each file by rename so a killed session leaves no half-written rule, ignores record entries that are not plain rule file names, does not let an older copy of the plugin put its rules back over a newer copy's, and never stops a session from starting. The hook has the `startup` matcher, so it runs on a fresh start only (checked in live sessions: it fires on a fresh start and not on a resume); the `ask_level` hook still runs on every session start, because its context line has to be added again after a resume or compaction. A run with nothing to do takes about 27 ms, 22 of them Node starting, and prints nothing. Rules go under the config dir (`CLAUDE_CONFIG_DIR` respected); references always go under `~/.claude`, the path the rules cite. Claude Code reads the rules folder before the hook runs, so newly written rules load by themselves only from the next session; for the session that wrote them the hook adds a note to the context that lists those files and asks Claude to read them first (checked in a live session: all 14 always-loaded rules were read and followed), and one message tells the person. Subagents started in that one session do not get the note. `setup-rules.sh` now links from the new folders and is only for people working on this repo and for the shipped permission settings (13 tests in `tests/install-rules.test.mjs`).
- **Proof when you finish work** (`rules/nextc-claude/verify-before-claim.md`). Before saying work is done, Claude runs the cheapest checks that could show it wrong (the analyzer, type check or linter, the tests that cover the change, a direct run when it takes seconds), after the last edit, and reports each command with its result. What could not be proven is listed with what would settle it. Builds, simulators and full suites still follow the heavy-commands rule.
- **`nextc-hud`: proof tracker.** The mod follows which check commands ran after the last code edit, with no model call. The row and a line under the answer say `checked · flutter analyze ✓`, `check failed · …` or `not checked · 2 code files changed`, built from the commands that actually ran, so it does not depend on what the answer claims. A passing result counts only when the command's own exit status is the check's: a check that is piped (`flutter test | tail`), chained with `;` or `||`, or started in the background is listed as "result not seen". An in-place `sed`, a formatter that writes or a git command that replaces files makes an earlier check stale, like an edit. Each check has a fixed label, never the command line, and quoted text is ignored. When a turn ends with code changed and nothing checked, the mod asks Claude to verify and report the proof (`proof_followup`), in the same single message per prompt the critical-review check uses. `/hud proof` lists the checks; `verify_commands` adds a project's own; `show_proof_line` hides the line.
- **`nextc-hud`: project pane (`/hud project`).** Tasks by milestone with bars from `docs/tasks.md`, the path from explore to ASO, the build timeline from the buildlog, quality (unreviewed critical files, proof state, the review ledger) and the week's cost sparkline with the skills used most, in bordered blocks with four tabs (keys 1 to 4), two columns from 96 columns of width. `[next task]` puts a request for the next open task in the prompt box. Read-only; it collapses to one line and is closed only by the user.
- **`nextc-hud`: usage (`/hud usage`).** The session history now records the skills and agent types each session used and the cost of the turns that used each skill. `/hud usage` shows the last 30 days and lists the installed skills that were not used.
- **`/product-review` (`nextc-product`): check a shipped product against its memo's kill criteria.** The decision memo already names experiments with thresholds and kill criteria; nothing read them again once the product had users. `/product-review` takes each criterion, measures it, and reports met, missed, too early or unmeasured with the numerator, denominator, window and the id of the recorded measurement, then applies the memo's own `if_missed` / `if_met` rules: a missed kill criterion wins, anything too early, unmeasured or drafted without confirmation gives "No conclusion yet" with what blocks it. `scripts/review-check.mjs` (commands `init`, `parse`, `validate`, `sql`, `check-bytes`, `record`, `rating`, `verdict`, `conclude`, `table`, `report-check`; 23 tests in `tests/review-check.test.mjs`) computes every number and prints the report's table rows and conclusion itself; `report-check` passes a report only when its Conclusion section is that text and nothing else, its Criteria section is that table and nothing else, and no other table line names a criterion. A proportion is judged on its Wilson 95% interval, so 9 of 55 against a 20% line is "too early, leaning missed" with the number of users that would settle it; a count waits for its planned sample or date and a rating for its minimum sample, so nothing is called from one early reading. `record` keeps three numbers and a short plain-text window, refuses a result that carries a user id, an email, a review author or a key-like string, accepts a BigQuery number only with the hash of a query this run rendered for that criterion, and accepts a zero only once the event was seen in the census. Sources in v1: BigQuery (GA4 or Firebase export) through the session's connector, with SQL templates rendered from validated values (dates in order, at most 400 days, cohort closed, nothing later than 3 days before the review date, which cannot be in the future) and a dry run checked against a bytes cap before each query; the public App Store rating (`rating`, Apple's iTunes Lookup, checked once against the live store); and numbers the founder reports, always labelled. The skill needs no key, does not pre-approve queries (each one asks, showing its SQL) and pre-approves file edits only under `docs/product-review/`. A memo without the criteria block gets criteria drafted from its tables: a threshold is read only when it states one percentage and one direction with no negation, and a drafted criterion blocks any conclusion until the founder confirms it. A stop or pivot conclusion gets one independent check by `product-collision-analyst`. The review never edits the memo; it offers `/product-explore --update`. Three eval cases with invented products (`pr-plantrill`, `pr-brinekin`, `pr-quibnote`). Not done yet: the SQL templates have not been run on real data, only `exact_day` retention has a template, DAU/WAU has none, and App Store Connect and Play readers are a later step.
- **`/product-explore` writes a `criteria` block in the memo** (`references/memo-template.md`, `judgment.md` J5 and J6): one JSON line per experiment and kill criterion with the metric, the events the product must emit, the comparison and threshold, the window, the planned sample, the source and what follows if it is missed or met. It repeats the thresholds of the two tables in a form `/product-review` can read exactly; the block is outside the word budget.
- **`/flutter-visual-proof` (`nextc-flutter`): see a Flutter screen without a simulator.** The skill renders the screens a change touched to PNG with one `flutter test` run of a render harness (`tool/visual/render.dart`, `screens.dart`, `screens_test.dart`, copied into the project on first use), using the app's own fonts from `pubspec.yaml`, Roboto, Material and Cupertino icons, its themes, its locales and real shadows. Claude then reads the images, compares them with `docs/design.md` and the ui-ux-design rule, and reports each layout exception (every distinct one, not only the first) per screen, locale and text scale. By default it renders every locale at scale 1.0 plus the two longest locales at 1.5, where translated text overflows first. Screens are listed in a registry with their fixture data (`references/fixtures.md` says which recipes were run and which are from memory); a changed screen with no entry is reported as not rendered, never skipped silently. A fixture or theme that throws becomes a line in the report, and a screen's pending timer does not fail the run. The harness needs only `flutter_test` and Dart 3, and adds no analyzer findings to the project. The previous run is kept beside the new one for before and after. Measured on Flutter 3.44.0: 2 to 5 seconds a run on a small app. It cannot show platform views, real network images, device safe areas or gestures, and says so in its report.
- **`nextc-hud`: a visual-proof run is not counted as a check.** The proof tracker ignores `flutter test tool/visual/...`, because the render harness exits 0 whatever the layout looks like; an analyzer or test run is still needed for `checked`.
- **`nextc-hud`: model advice (`/hud advise`).** The session history now also records which model each turn ran on, the model each agent ran on, and whether an agent's call named a model at all. `/hud advise` shows the last 30 days by model and points at three things: an agent type spawned three or more times with no model in the call that ran on an Opus or Fable session model (agents the roster lists are left out, because their definition names a model), an agent that ran above the tier `agents-roster.md` gives it (and the text says so when the roster file is missing), and a skill whose turns were 80% or more on a Fable-tier session model. It says which model ran, not whether a cheaper one would have been enough, and makes no model call (`hooks/lib/proof.ts`: `adviceText`, `parseRoster`, `tierOf`; four tests).
- **`docs/qc/critical-reviews.md`**: the repo's own review ledger, started with the two critical-review passes over the rules installer and the product-review script (both "fix first"; what was fixed and what was left is in each entry).
- **`nextc-hud`: lesson capture.** A prompt that opens like a correction makes the row offer `[ save lesson ]` for three turns; pressing it (or `/hud lesson`) puts a `/learn-eval` request quoting the correction in the prompt box (`lesson_capture`).
- **`nextc-hud`: handoff at the right moment.** When context first reaches "act now", the mod writes `.claude/handoff.md` in the background with one tool-less model pass over the session's own transcript, in the form `/session-handoff resume` reads. Only a reply in that form is written, the previous handoff is kept as `.claude/handoff.prev.md`, and the file starts with a note that it is unverified model text to read before resuming (the pass is told to treat tool and file output as data and to name secrets' locations, not values). `[ fresh start ]` then offers `/clear`, writing the handoff again first if you worked on after it. It does not run above `auto_handoff_max_tokens` (400,000), because the pass re-reads the whole conversation; `/hud handoff write` does it on request (`auto_handoff`). This is the second file the mod writes by path and its second model call.
- **`nextc-hud`: build warning.** A build or upload command that starts while critical files are unreviewed or code is unverified gets one toast (`upload_warning`). It never blocks.
- **Review ledger.** After a `critical-reviewer` pass the lead appends the reviewer's ledger entry to the project's `docs/qc/critical-reviews.md` (`rules/nextc-claude/practices.md`; the agent ends its report with the entry: date, verdict, files, model, findings, outcome). The project pane reads it.
- **Build skills warn, and never refuse, before building.** `/flutter-build` runs `flutter analyze` in pre-flight and both `/flutter-build` and `/unity-build` check whether critical logic changed since the last build with no ledger entry; either gives a one-line warning and the build carries on.
- **`/release` project skill** (`.claude/skills/release/SKILL.md`), for this repo only and shipped by no plugin: decide the version, run every check, bump, write the release entry, commit, push and update the installed plugins.
- **Rules evals: two new cases** (`proof-on-done`, `review-ledger`; 26 in all). With the new rules a one-run pass over all 26 cases is 26 of 26 (23 of 26 before), and the cases that guard against unasked tests and builds still pass. The first wording of the proof rule passed 2 of 3: a run proved its change by a direct run without looking for the covering test, so the rule now says to search for covering tests first. `rules-evals/RESULTS.md` has the entry.
- **"Before every commit" in `CLAUDE.md`.** The repo has no CI, so the table says which checks to run for which change, after the last edit, before a commit is called ready.

### Changed
- **`rules-evals/lib.mjs` reads the rules from where a ref keeps them** (`nextc-core/rules/nextc-claude` now, `rules/nextc-claude` in older commits), so a before/after eval across the move still compares the same files. The rule files moved without a change to their text, so no rule eval was needed for the move.
- **Docs and descriptions follow the new layout:** `README.md`, `CLAUDE.md`, `enterprise/README.md` and `rules-evals/README.md` no longer say the rules are installed by `setup-rules.sh`; the `ask_level` option text points at `install_rules`; the marketplace and plugin descriptions of `nextc-product` and `nextc-flutter` name the new skills; `nextc-product/evals/README.md` lists the three `pr-*` cases.
- **How much Claude asks is now a setting: `ask_level` in `nextc-core` (`/config`), `normal` by default, `less` for the behaviour the rules had since the 2026-11-16 rewrite.** At `normal` Claude asks before a heavy process nobody asked for, when a request has two readings that lead to different work, when a product choice comes up, and before retrying a failed store upload. At `less` it skips the heavy check and tags the claim, picks the sensible reading, keeps real product choices for one question per task and retries a diagnosed upload. Both levels never start a heavy process unasked, both run what an invoked skill exists to do without an extra question, and a standing "don't ask" makes one task behave as `less`. `rules/nextc-claude/heavy-commands.md` holds both columns; `stop-and-diagnose.md` and `practices.md` point to it. A `SessionStart` and `SubagentStart` hook (`nextc-core/hooks/hooks.json`, `scripts/ask-level.mjs`) adds the line `nextc ask level: less` when the option is `less` and nothing otherwise, so the default level costs no context. `nextc-hud` follows the same setting: its `critical_followup` and `proof_followup` options now default to `auto`, which sends the follow-up at `less` and puts it in the prompt box at `normal` (or when `nextc-core` is not installed); `send`, `fill` and `off` still fix it. The mod reads the level from the merged settings (`pluginConfigs`), and `/hud status` shows it. **If you relied on the ask-less behaviour, set `ask_level` to `less` after updating.** The option uses a fixed list of choices (`options`), which the plugins reference says needs Claude Code 2.1.271 or later: on an older version `nextc-core` does not load. New test file `tests/ask-level.test.mjs`; new eval case `heavy-ask-normal` and a `level` field for cases (27 cases).
- **`scripts/bump-version.mjs` refuses a version that is not higher than the current one** unless `--force`, with a test. Installed copies only pick up a higher version; an explicit lower target was accepted before.
- **`nextc-hud` no longer only observes outside the critical check.** Besides that check's model call, the follow-up message now also asks for proof, and the handoff writer adds a model pass and a file. Each has its own off switch, and none runs in `claude -p` or autopilot runs.
- **The "used this turn" hooks are always registered**, with the turn line itself still behind `show_used_line`, so skill use is counted for `/hud usage` when the line is off.

### Fixed
- **`nextc-hud`: the row no longer shows a stale context figure after a compaction with no reply after it.** Claude Code can now compact a session while it is idle ("Compacted while idle, before the prompt cache expired"). The mod counted that compaction but kept the old reading, so the row still said for example `ctx 21% heavy (206k of 1M)` and still offered `[ compact ]`. A compaction now replaces the reading with the size the engine reports for the compacted conversation, or blanks it to `ctx –` when it reports none, so the level and the actions follow (`hooks/lib/coach.ts` `applyCompactEvent`; two tests).


## 2026-11-16

### Added
- **Released 1.8.0** with the `nextc-hud` additions below; all 9 plugins and the marketplace moved from 1.7.0 to 1.8.0.
- **`nextc-hud`: always-on session row, session coach and a project run monitor** (1.8.0).
  - A row above the prompt is now always visible in interactive sessions: context used (with tokens when the window is wide), compactions this session, the session cost estimate, 5-hour and weekly rate-limit use, and running or idle agents. It never wraps; at 80 columns it still shows context, compactions and cost. Reason: 34 of 77 interactive sessions passed 200k tokens and there were 178 compactions in seven weeks.
  - The session coach turns the row to "heavy" at 50% context or 200k tokens and to "act now" at 80% or from the third compaction, with one toast per crossing per session. All four thresholds are options in `/config`.
  - A new immediate `/hud` command (`status`, `on`, `off`, `compact`, `handoff`, `coach`, `runs`, `watch`). The compact and fresh-start actions fill `/strategic-compact` (or a focused `/compact`) and `/session-handoff save` into an empty prompt box. They never send a prompt and never replace a draft.
  - Compactions are counted from the `session.compact` event, or from a sharp drop in context tokens where that event is not visible to the mod, and never twice.
  - The project run monitor reads what the skills already write: `/flutter-build` and `/unity-build` buildlogs and log times, `/product-explore` and `/idea-explore` state and evidence index, the ASO pipeline state and kickoff state. One live run shows as a segment in the row; `/hud watch` opens a read-only pane. A quiet run says "quiet Nm" before it is marked stale.
  - Still observe-only: no process, network or model calls, no prompt submitted, and the autopilot `STOP` file remains the only file it writes. `$.prompt.fill` is the one new capability. In `claude -p` and cloud sessions it starts no timers and reads no files. 160 tests (was 31).
- **`/autopilot`: relaunch recovery, standing defaults, live status and launcher commands** (`nextc-core/skills/autopilot`, `nextc-core/scripts/autopilot-*.mjs`).
  - When a launch ends mid-step, the launcher writes an `R` ledger entry and the next launch continues from the earlier worker's uncommitted edits. It no longer starts a second worker blind (four duplicate workers were spawned this way in past runs).

It is now a local script, `hooks/scripts/block-no-verify.js`, adapted from the package (MIT). It splits a Bash call into its commands, respecting quotes, and checks each git command's own words. `-m` values and comments are skipped. Quoted text that contains `git` is checked too, because `sh -c`, `eval` and `$(...)` run it. Tested on 36 cases, with the old package run on the same cases:
  - **Old false positives, now allowed (6):** `-n` from `grep`, `sed`, `head`, `echo` or another command's arguments next to a commit, and a commit message of `-n`.
  - **Old misses, now blocked (4):** `git commit -an`, lowercase `core.hookspath`, `-ccore.hooksPath=…` and `g\it commit -n`.
  - **The rest:** every other case gave the same result in both.

  The hook no longer runs `npx`, so it works offline. It now has `onFailure: "block"` like the other safety gates. The package's GitHub MCP tool check is dropped: the hook only matches Bash calls, so that check never ran.
- **Autopilot's decider wasn't being asked.** In the first demo run, the worker settled "what does `cli.js` do with no name?" itself and logged it as its own decision, so `autopilot-decider` never ran. Workers now return `needs-decision` for any user-visible choice the plan leaves open. The orchestrator also routes any such worker decision to the decider and redoes the work if the answer differs.
- **Autopilot's report said "Cost: not recorded".** The run can't see its own final cost, so the launcher now prints it at the end and appends each launch's cost to `~/.claude/autopilot/<run-id>/result.json`. It uses the session's last `result` event, because `total_cost_usd` is a running total. The demo run's transcript gives $0.91.
- **The autopilot Stop hook interrupted correct waiting.** Workers run as background agents, and the orchestrator ends its turn to wait for one. The hook blocked that 4 times in the demo run, and the orchestrator filled the gap with `sleep` polling. The hook now allows a turn to end while a step is `in_progress`, and run mode tells the orchestrator to wait for the notification instead of polling.
- **Autopilot state files are owner-only.** `stop-hook.json` was written as 0644; it is now 0600, like the launcher's files, and plan mode writes `approved.json` with `chmod 600`.
- **Autopilot no longer blocks harmless commands that mention a hard-stop word.** The launcher's deny rules were loose globs such as `Bash(*git*push*)`, so `git log --grep=push` or `cat deliver.md` was denied. The guard hook now parses each command and checks only the command word and its subcommand, and the deny rules are now exact prefixes. Checked against 46 commands (14 harmless ones allowed, 32 hard-stop forms blocked) plus 16 regression cases for the file guard, STOP and the Stop hook. One false positive remains on purpose: a heredoc whose text contains `git push` is blocked, because the guard can't tell data from a script fed to `sh`.

### Added
- **`rules-evals/tune.mjs`** — automated tuning for one rule file, after the propose → probe → compose loop in [google-research/harness2](https://github.com/google-research/harness2). harness2 can't drive Claude Code (its executors are OpenCode and Codex), runs on Linux with Vertex AI, and is a 0.1.0 research release, so the idea was borrowed and the code was not. Usage: `node rules-evals/tune.mjs --target <rule> [--goal fix|trim]`.
  - **How it works:** it scores the working-tree rules on the eval cases, then asks a tool-less `claude -p` for up to 3 rewrites of the target, each with a different strategy. Every candidate is run on the same cases.
    - Only cases whose `rule` names the target are scored. The rest guard against regressions.
    - The winner must beat the baseline on those cases (or, in `trim` mode, match it in fewer characters) without losing any case that passed every baseline run.
  - **Safeguards:**
    - The proposer sees each failure's task, reason and reply, but never the grader code.
    - Runs that crashed or hit a cap count as infra failures, not rule failures; a baseline with any stops before proposing.
    - Rewrites that change nothing, or break the size limits, are rejected. A fix may grow at most 15%; a trim must stay at least half the original size.
    - It prints the worst-case cost up front and stops starting runs at `--max-spend`.
    - Without `--apply` the script never edits `rules/`: the winner lands in `results/` as a file plus diff for review, marked unconfirmed.
  - **`--apply`:** it re-runs the baseline and the winner with fresh, larger samples (`--confirm-runs`, default 5).
    - These runs use bundle copies, so a winner that fails confirmation never goes live, even briefly.
    - Only if the winner holds up does the script write it into `rules/<rule>.md`. That file is live in every new session at once through the `~/.claude/rules` symlink.
    - It refuses to start when the rule file has uncommitted edits, so `git checkout` is a clean undo.
    - The lesson records "applied" or why confirmation failed.
    - Tested in a throwaway clone with a fake `claude`: confirmed-and-applied, failed confirmation (file untouched), a dirty file refused, and no flag (file untouched).
  - **Flag parsing:** `rules-evals/lib.mjs` `parseArgs` now treats a flag followed by another flag, or by nothing, as a boolean. Before, a bare flag swallowed the next argument.
  - **Review:** a code review found six medium issues, all fixed before release. The worst was that failures from other rules could steer the proposer and the winner.
  - **Lessons:** each run appends its scored outcome to `rules-evals/LESSONS.md`, which the next proposer for that file reads. This mirrors harness2's persistent "improvement harness".
  - **Checked so far:** dry runs against a fake `claude` binary exercised fix, trim, an infra failure and bad input at no model cost.

- **`rules/nextc-claude/ui-ux-design.md` (new §1b under rule 1, plus an Enforcement bullet)** — a categorical/semantic colour palette (by type, family, status, owner, tier) must now pass three tests before it is proposed, and a "no" on any one is a no: (1) **does the accent already mean something else** — a palette that assigns the accent to a category makes it mean two things at once on every screen where that category is common; (2) **does every hue clear the text-contrast floor at the size it will actually be read** — a hue picked for a fill is usually illegible as small text, so expect to need lightened variants and treat "this needs new tokens" as a signal the change is bigger than it looks; (3) **could the colour answer a question the screen is asking** — a diagram, shape, chart mark or icon that *is* the question must never be coloured by its own answer, and this one is a hard stop rather than a trade-off, fixed by pulling the encoding off that element everywhere rather than by a per-screen exception (an exception is a rule someone has to keep remembering). Rationale: encoding a category as a hue is the most tempting way to make a dense screen legible and the most common way to break rule 1; it is also a system rather than a screen, committing every surface that draws the category. Test 3 comes from a real case — an ear-training quiz that draws one chord shape and asks the learner to name it, where colour-coding the diagram by chord family answered the question before the shape could be read.
