# Output contract

Every run leaves a small set of decision-shaped files. No file restates another: the report points to
the metadata files and the keyword table instead of copying them, and the one table it contains is
generated by script.

```
aso/
  intake.json                 answers from the intake (no keys, no key paths)
  report.md                   the decision document (about 1,200 words)
  metadata/<locale>.json      proposed metadata, PASSED by limits-check
  metadata/<locale>.check.md  limits-check result (written by the script)
  keywords.csv                observed keyword table (written by the script)
  plans/<topic>.md            optional: creative, localization-<locale>, reviews, tracking
  data/                       raw evidence: listings, observations, reviews, cache, checks
  .pipeline-state.json        written only by state.mjs
  .snapshots/<time>/          previous runs, for "what changed since last run"
```

## `aso/metadata/<locale>.json`

One file per locale. `current` is copied verbatim from a listing file on disk (or `null` when the
store does not expose the field and no key or user input supplied it). `proposed` is `null` for "no
change".

```json
{
  "locale": "en-US",
  "country": "us",
  "decision": "update",
  "sellerName": "Example Ltd",
  "brandTerms": ["Nestly"],
  "competitorBrands": ["Day One", "Journey"],
  "currentSources": ["aso/data/listing-ios-us.json", "aso/data/asc-en-US.json"],
  "ios": {
    "name":            { "current": "…", "proposed": "…", "why": "keywords.csv: 'friendship journal' open, not in top 50" },
    "subtitle":        { "current": null, "proposed": "…", "why": "…" },
    "keywords":        { "current": null, "proposed": "word,word,word", "why": "…" },
    "promotionalText": { "current": null, "proposed": "…", "why": "…" },
    "description":     { "current": "…", "proposed": null, "why": "conversion copy; unchanged" }
  },
  "android": {
    "title":            { "current": null, "proposed": "…", "why": "…" },
    "shortDescription": { "current": null, "proposed": "…", "why": "…" },
    "fullDescription":  { "current": null, "proposed": "…", "why": "…" }
  }
}
```

Fields allowed: iOS `name, subtitle, keywords, promotionalText, description, whatsNew`; Play
`title, shortDescription, fullDescription`. Omit a platform the app is not on. `competitorBrands`
lists every competitor named in the intake or observed in the top results you discuss.

After writing a file, run `limits-check.mjs aso/metadata/<locale>.json --embed aso/report.md` until
it prints PASS. Never hand-type a length; the table carries the exact count.

## `aso/keywords.csv`

Built by `store-lookup.mjs keywords-csv` from `aso/data/observations-*.json` plus your judgments in
`aso/data/term-notes.json` (`{ "<country>": { "<term>": { "relevance": "core|adjacent|off", "placement": "name|title|subtitle|keywords|shortDescription|description|none", "note": "…" } } }`).

| Column | Meaning |
|---|---|
| `observed_competition` | Tier computed by the script from the top 10 (below) |
| `top10_title_matches` | How many of the top 10 results have every word of the term in their name |
| `top10_median_ratings`, `top10_max_ratings` | Rating counts of the top 10 in that storefront (proxy for incumbent strength) |
| `results_returned` | Apps the API returned (fewer than 10 means a thin result set) |
| `app_rank` | The app's position in the API results, `not in top N`, or `no app` (pre-launch) |
| `search_volume`, `volume_source` | `unavailable` unless an optional provider supplied a number and is named |
| `relevance`, `placement`, `note` | Your judgment, labelled as such |
| `retrieved_at`, `source_file` | Provenance of the observation |

### Observed-competition tiers

These describe what the store showed, not demand. Thresholds live in `store-lookup.mjs`
(`TIER_RULES`) and are heuristics.

- **contested** — 5 or more of the top 10 names contain the term, or their median rating count is 10,000 or more.
- **open** — 2 or fewer of the top 10 names contain the term and their median rating count is under 1,000.
- **mixed** — anything between.
- **thin** — the API returned fewer than 10 apps. Few results can mean an underserved term or a term nobody searches; the data cannot tell which.

Never call a term "uncontested", "high volume" or "low difficulty". Say "open in US on 2026-11-16:
1 of 10 top names contain it, median 240 ratings".

## `aso/report.md`

About 1,200 words. Sections, in this order:

1. **Decision this run serves** — one paragraph: app, storefronts, the decision from the intake, data used (with dates) and data unavailable.
2. **What to change, in priority order** — numbered. Each item: the change; why (the observation that supports it, cited as `keywords.csv` row / data file + date / URL); expected effect stated as direction plus what evidence supports it ("should improve visibility for 'friendship journal', where the app is not in the top 50 today and the top 10 are small apps") — never a percentage you cannot source.
3. **Current → Proposed** — one embedded table per locale, generated by `limits-check.mjs --embed`. Do not edit inside the markers.
4. **What could not be determined** — volume, Play search, subtitle of competitors, anything a missing key blocked.
5. **What to measure next** — the few numbers to read after the change ships (App Store Connect impressions and conversion for the changed storefront, ranks for the targeted terms re-observed with `store-lookup.mjs observe`), and when.
6. **What changed since last run** — paste `state.mjs diff` output, or "first recorded run".
7. **Sources** — the data files with their retrieval dates and the URLs of any store pages quoted.

Optional sections (only when the run's decision needs them) live in `aso/plans/` and are linked from
item 2, not summarised again.

## Plans (`aso/plans/<topic>.md`)

Written by `aso-specialist` workers. Each opens with the decision it serves, cites the data files it
used, and ends with "Unknowns". Budgets: creative 500 words, localization 400 words per locale,
reviews 600 words, tracking 400 words.
